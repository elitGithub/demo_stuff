# Scribe error display and local key changes

The operator approved the [design](../specs/2026-11-19-scribe-error-display-design.md) on 19 November 2026. This plan is up for approval. Paths below are relative to `zeta-dm-memory/`. The scope is Zeta Scribe in one Tampermonkey installation and browser profile. The standalone bench has its own session key.

## Task 1 — Separate the current activity from actionable errors

**Files** — `scribe/page/ScribeKeeper.js`, `scribe/page/ScribeLive.js`, `scribe/page/PanelView.js`, `scribe/page/ScribePanel.js`, `scribe/page/PanelStyle.js`. Use `scribe/core/ScribeGateway.js` as the reference for masked diagnostics. Update `tests/scribe-live.test.mjs`, `tests/scribe-keeper.test.mjs`, `tests/scribe-panel.test.mjs`, and affected assertions in `tests/scribe-boot.test.mjs` and `tests/scribe-whole.test.mjs`.

1. Use the actual history callback count in `ScribeKeeper.history(keeper)` for “Reading chat history from Zeta · 155 messages”. Retain the zero, singular and plural cases. Make `PanelView.headline(keeperView, liveView, cloudView)` return the activity or room state. Move the appended warnings into a separate display. Preserve the current loading, watching, conflict and paused states and their controls.
2. Expose role and masked reason as separate fields for each active scene, check or recap error from `ScribeLive.view(live)`. Read the existing saved `failing.scene`, `failing.check`, and exhausted `untold.reason` directly. Use the gateway's status/finish information where available. For existing saved strings, recognize the gateway's anchored diagnostic format and the legacy leading `HTTP 401` format. A number inside quoted provider prose is insufficient for classification. Take the service from the operation that failed. Trace keeper errors to the operation before assigning them to Zeta or OpenRouter. Retain a generic description for an ambiguous legacy keeper error.
3. Add `PanelView.problems(keeperView, liveView, cloudView)` returning ordered display records with service, cause, affected operations, short label, explanation and masked details. Combine equivalent causes from the same service. Group unknowns only when their masked reasons match. Preserve materially different provider reasons. Emit the approved two-role copy verbatim for the reported 401. Use “Scene updates”, “Story checks”, and “Story recap” only for work actually affected. Use Cloudflare's refused phase for the Worker-key message and the existing Zeta login signal for the sign-in message.

| OpenRouter evidence | Explanation for the operator |
| --- | --- |
| HTTP 401 | OpenRouter rejected the saved API key. Name the affected work and point to **Settings → Save key**. |
| HTTP 402 | OpenRouter reported a credit or spending limit. Point to the OpenRouter account or key limit. Keep Scribe's local daily budget distinct. |
| HTTP 429 | OpenRouter is limiting requests. Report a scheduled retry only while one is pending. |
| HTTP 5xx or transport failure | Identify a service error or an unsuccessful connection according to the evidence. Avoid claiming an outage on a connection error. |
| Truncated answer or unusable response | Explain that the answer ended early or supplied no usable result. Identify the affected work. |
| Unrecognized reason | Name the unsuccessful operation and direct the operator to the masked detail in Progress. |

4. In `ScribePanel.redraw`, render an activity line, one text element per distinct problem, and a compact summary. Add stable IDs `scribe-problems`, `scribe-problems-compact` and `scribe-problem-details`. Use the existing expand control and accessible status conventions. In the collapsed phone strip show “OpenRouter key rejected” for one auth issue or “2 problems” for two distinct causes. Ensure text wraps without hiding the toggle. In Progress render the active masked detail even after a reload empties `live.calls`. Retain call history separately. Never use provider text as HTML.

**Break it.** Replay the 155-message example with two identical saved 401s, redraw twice and reopen the room. Assert one Zeta activity, one warning naming both operations and one key action. Recover only the scene, then the check, and verify each redraw. Exercise three affected roles, different unknown reasons, a provider reason containing “401” on a 503, simultaneous Zeta login and Worker/OpenRouter credential failures, 200 with a length cutoff, an HTML-looking reason, and a diagnostic containing a synthetic key. Verify masking in each output. Inspect the collapsed and expanded panel at 320 CSS pixels with two distinct problems.

## Task 2 — Propagate a successful save through Tampermonkey

**Files** — `scribe/userscript.header.txt`, `scribe/page/ScribeStart.js`, `scribe/page/ScribeBoot.js`, `scribe/page/ScribePanel.js`. Reuse `scribe/page/ScribeStore.js`'s existing `key(storage)` and `setKey(storage, key)`. Extend `tests/support/FakeStorage.mjs`, `tests/support/WholeTab.mjs` and `tests/support/PanelHarness.mjs`. Update `tests/scribe-boot.test.mjs`, `tests/scribe-pack.test.mjs`, `tests/scribe-panel.test.mjs` and `tests/scribe-whole.test.mjs`.

1. Add grants for `GM_addValueChangeListener` and `GM_removeValueChangeListener`. In the **top-page** adapter expose `storage.watch(name, changed) => unsubscribe`. Register a callback that invokes `changed()` without forwarding Tampermonkey's old or new values. The authoritative value remains the one string at `ScribeStore.name(ScribeStore.Settings.Key)`. Keep the existing Worker-key slot independent. The userscript frame needs no new storage access. [Tampermonkey listener API](https://www.tampermonkey.net/documentation.php?locale=en#api:GM_addValueChangeListener)
2. Register one listener per top-page boot, spanning room navigation. Subscribe and establish a baseline before mounting Settings. Add `ScribeBoot.refreshKey(boot)` to reread the authoritative string, compare privately in the userscript sandbox, and return whether the effective value changed. Track an in-memory change counter for invalidating pending work. Treat delayed notifications as a signal to reread. Dispose of the subscription in `stop()`. Reconcile on visibility restoration, page restoration, and before saving a field or issuing a model request. On storage read failure, report a local storage problem and refrain from using a cached credential.
3. Route `ScribePanel.saveKey(panel)` through one boot-owned save callback. On input, associate the draft with the current change counter. Before saving, reconcile storage and discard a superseded draft with a brief local notice. An intentional new entry after reconciliation can be saved. After a successful write, reconcile immediately in the originating tab. A local listener echo must not run recovery twice. Preserve the existing explicit local retry on a deliberate re-save of the same key. Failed writes must not announce success. Do not populate the password field from storage.
4. On change, clear the older key input and its obsolete validation state in every mounted pane. Keep other unsaved settings intact. Readers use the existing keeper/live rekey paths once per observed change, subject to room ownership, cloud lease, budget and pause state. A watching or initializing tab refreshes the UI immediately and defers eligible recovery until its room can read. Guard asynchronous callbacks against a closed room or stopped boot.

**Break it.** Simulate two rooms with independent readers and a third tab watching one room. Save in the watcher while both readers are parked on 401. Each reader recovers once, the watcher makes zero model calls, and every password input is blank. Delay and reorder notifications across two successful writes, suppress delivery while a tab sleeps, attempt a stale save on wake, open a new tab, and switch rooms while a notification is queued. Check the final key at the next credential use. Inject a refused write, unchanged-key save, duplicate notification and stop/start cycle. Confirm that key propagation alone generates zero network requests with model work idle.

## Task 3 — Prevent retries and late errors from using a superseded key

**Files** — `scribe/page/ScribeBoot.js`, `tests/scribe-boot.test.mjs`, `tests/scribe-whole.test.mjs`, and `tests/support/WholeModel.mjs` for held responses. Exercise the existing `ScribeGateway.retry`, `ScribeLive.rekey` and `ScribeKeeper.rekey` paths.

1. Move key selection inside the per-attempt callback in `ScribeBoot.call(session, role, system, user, bill, gate)`. Capture the change counter with the actual key used to build that request. Recheck at the final send boundary immediately before `boot.request`, including after any queued microtask or backoff. If superseded before dispatch, discard the prepared headers and prepare the attempt with the current key. An empty or unreadable key must prevent transmission.
2. If an already-dispatched old request returns an authentication failure, reconcile **before** handing the outcome to the keeper or live helpers. While the original job is eligible, continue it once for that observed change with the current key. A repeated 401 on that same current key follows normal failure handling. Preserve the normal reader/lease and budget checks on resumption. Coordinate with Task 2 so the old job's replacement and the notification cannot start duplicate work. Closed, paused, superseded-room or readerless jobs must not restart. Preserve valid completed results, original billing and existing Force stop semantics.
3. Cover initial requests, the gateway's delayed retries, the outer Force stop retry loop, and both `ScribeBoot.ask` and `ScribeBoot.counted`. Propagation requires no model validation call, Worker write containing credentials, extra endpoint, dependency, schema change or server deployment.

**Break it.** Hold a 401 for key A, save B in another room, release A's response, and verify the panel never reinstates A's warning. Repeat with a 503 sleeping before retry and with an already prepared request waiting for dispatch. Record the authorization header in the synthetic transport and require B on each subsequent dispatch. Exercise a second rotation, new-key rejection, reader handoff, a budget exhausted before resumption and a late billable result. Check actual request count, per-room spend, and the surviving error after each case.

Assert it is absent from all other destinations, including after a provider echoes a secret in a failed response. Inspect the compact strip, keyboard expansion, full warning and post-recovery panel. Record simulated and observed browser results separately.

For each task that modifies shipped code, generate the expected bundle in memory with `ScribePack.build(read)` from `scribe/pack.mjs`, update `scribe/scribe.user.js` through a visible edit, and compare the resulting file to the in-memory build. Account for the checkout's established CRLF conversion when comparing. Run each affected suite by name, for example `node --test tests/scribe-boot.test.mjs`, and always run `node --test tests/scribe-pack.test.mjs`. Final regression suites are `scribe-gateway`, `scribe-store`, `scribe-cloud`, `scribe-keeper`, `scribe-live`, `scribe-panel`, `scribe-frame`, `scribe-boot`, `scribe-whole` and `scribe-pack`. Record actual pass/fail totals and any unavailable live checks.

Execute one task at a time after operator approval. For each, a native OpenAI implementer writes the code and then the regressions. A separate native reviewer must reproduce any finding. The orchestrator checks each reproduction and proposes any fix round to the operator. The next task waits for the operator's review and commit.
