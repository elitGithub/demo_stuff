# Changes Universe makes to Aspect: Vocalia

Universe bundles Aspect: Vocalia 1.0.4 (`packages/st-aspect-vocalia-1.0.4.tgz`) unchanged. The package and the lockfile stay as they are. Universe changes Vocalia only while the build copies it into SillyTavern:

1. Each function listed below is renamed in Vocalia's `index.js` from `function <name>(` to `function vocaliaBase_<name>(`. Each name must occur exactly once, or the build stops and names the function.
2. `extension/vocalia-overrides.js` is appended to the end of the file. It declares Universe's version of each function under Vocalia's original name, so every call inside Vocalia reaches Universe's version, and Universe's version calls Vocalia's own under the `vocaliaBase_` name.

The list of renamed functions is not kept by hand: it is every top-level `function <name>(` in `extension/vocalia-overrides.js` whose name does not start with `universe`. Universe's own helpers, its reason strings (`universeReasons`), its name for the Continue action (`universeContinueAction`) and its two flags start with `universe`, and no Vocalia name does.

## When the narrator speaks

With a narrator in the group, the narrator speaks only when one of these holds:

- (a) the narrator extension's `firstSpeaker` names it for the player message being answered;
- (b) it is the only present or remote member;
- (c) it continues or regenerates its own reply.

Every change below serves this rule, and empty Send and Continue follow it whatever the chat ends with.

## The switch

A narrator is in the group when `globalThis.universeNarrator` exists (the Universe: Narrator extension provides it) and one of the group's members is the narrator by its `isNarrator` and is not muted (`disabled_members`). Without one, every override is identical to Vocalia's own: it returns what Vocalia's function returns for the same arguments and does nothing else. Vocalia then behaves as the author wrote it: with the narrator card deleted, removed from the group or muted, "Call Viola." brings Viola in again and a player's message can mark someone as having left. A muted narrator can never speak, so it counts as not there; otherwise nobody could bring anyone in.

## The narrator is always present

- When the narrator's own reply would make it leave (`participationNextTurn` read as departing, which Vocalia applies at lines 5142-5144) and Vocalia accepts the reply, Universe hands Vocalia a copy of the block with `participationNextTurn` set to `idle`. Vocalia then records the reply exactly as an idle one: the narrator stays present, stays the last speaker, keeps its `speakingTo`, and waits for the player if it addressed them. `onReplyBlock` still receives the reply's own block.
- When the narrator extension names the narrator to speak first and Vocalia's own check says it is neither present nor remote (for example, it was marked absent in Vocalia's Status panel), Universe sets it present before handing it to Vocalia, so Vocalia's queue (`isRouteEligibleForQueue`, line 5674) accepts it. It then refreshes Vocalia's prompt, Status panel and saved state the way Vocalia's own summon does after `setPresence` (lines 3019-3022), so the next reply's prompt no longer lists the narrator as absent.

## The picking flag

Vocalia chooses who speaks next for a player's message in five functions, called pickers below. While one of them runs, Universe sets a flag that hides the narrator from three eligibility functions, so no rule in Vocalia's chain can choose it: not a reply's `speakingTo`, not the member waiting for the player, not the most recent speaker, not the last speaker, not the random or first fallback, and not a name mentioned in the player's message. The flag is cleared when the picker finishes or throws. Outside a picker the narrator is eligible as usual, so its own replies are routed.

The fifth picker is Vocalia's fallback for Regenerate and Continue (`getControlledActionFallbackTarget`, line 6895), used when Vocalia cannot tell whose message is being redone; Vocalia then writes a new message with `/trigger`. With a narrator in the group, Universe runs it with the narrator hidden for both actions, then asks `firstSpeaker` about the player message being answered, if there is one (see below), and a member it names replaces Vocalia's pick. Only when `firstSpeaker` names no one and Vocalia's own found no one is the narrator picked, and only when it is the only eligible member. Vocalia's Regenerate reaches the fallback only when the owner of the reply being regenerated is not a group member (lines 7026, 7051): a member removed from the group, a deleted card, or a name that is no member's. For Regenerate, the message being answered is the latest player message before that reply, from Vocalia's own `findLatestUserMessageBefore`, the one Vocalia records for the regenerated turn (line 7355). The narrator is a group member, so Regenerate or a swipe on its own reply never reaches the fallback, and rule (c) holds.

Regenerate asks `firstSpeaker` only when no reply survives between that player message and the replies Vocalia deletes, the window Vocalia's own `getTailRegenerateDeleteWindow` gives (line 6845). A surviving reply is one that is neither blank nor a system message, the same rule as for Continue below. SillyTavern hides a message by marking it a system message (`is_system`), so a hidden reply does not count, and Regenerate after a hidden narrator reply asks again. SillyTavern gives every reply its own `extra.gen_id` (`group-chats.js` line 600 for greetings, `script.js` line 6775 for group replies), so the window is usually only the reply being regenerated. Without this rule, regenerating a reaction to the narrator's answer would ask again about a message the narrator has already answered, and the narrator would speak twice in a row. When a reply survives, the fallback keeps Vocalia's pick with the narrator hidden, and picks the narrator only when it is alone. Replies without `gen_id` give Vocalia a wider window that reaches back to the nearest player or system message. When that is the player message, Regenerate deletes the narrator's answer too, and asking again is correct.

For Continue, a player message counts as unanswered when no non-blank reply follows it: system messages and blank replies (a failed, empty reply) do not answer it. Universe decides this with Vocalia's own `findLastAssistantMessageId` (line 6741), which skips blank replies, and `findLatestUserMessageBefore` (line 6754), so "blank" and "player message" mean what they mean to Vocalia. Vocalia's `getLatestUnansweredUserMessage` (line 3123) is not used, because it counts a blank reply as an answer. Continue reaches the fallback through Universe's `resolveContinueTarget`: with an unanswered player message, Continue answers that message, and Universe treats the fallback like the recovery, so a `Narrator:` message followed by a blank reply still gets the narrator. Otherwise Continue goes to the speaker of the last non-blank reply, found the way Vocalia finds the owner of a clicked message, so Continue after the narrator's reply stays on the narrator, and a blank reply after a character's answer goes back to that character. When that speaker is no longer eligible (it departed, was muted, or left the group), Continue takes the fallback with the narrator hidden and without asking `firstSpeaker`, because no player message is being answered; the narrator comes only when it is alone. This cannot keep the narrator from continuing its own reply, because its own last reply always takes the owner path: a muted narrator switches Universe off, and the narrator is present whenever it can speak. That presence is Task 2's doing: its `CHAT_CHANGED` and `GROUP_UPDATED` handler sets the narrator present, and a `firstSpeaker` pick brings an absent narrator back (above). Continue has no random rule, unlike empty Send: where empty Send would pick a present member at random, Continue can find no one and Vocalia shows its "no eligible speaker" warning. That gap is Vocalia's own; chats that start with cast greetings avoid it, because the greetings give Continue a previous speaker to go back to.

## Who speaks first

Four of the pickers answer a player message: the opening selector, the continuation selector, the recovery, and the Regenerate and Continue fallback (for Continue, only when a player message is unanswered; for Regenerate, only when no reply survives between its player message and the replies Vocalia deletes). Each asks the narrator extension who speaks first, with that message's number (`firstSpeaker`), and a member it names speaks alone. They differ in order. The opening and continuation selectors ask first, and run Vocalia's own with the narrator hidden only when no member is named. The recovery and the fallback run Vocalia's own with the narrator hidden first, then ask. While one of them runs Vocalia's own, it holds the question: an opening or continuation selector that Vocalia calls inside it runs as Vocalia's own and does not ask. In Vocalia 1.0.4 that happens in one place, the recovery, which Vocalia's empty Send calls and which calls the opening or continuation selector itself; the recovery asks, and the selector inside it does not. The empty-Send picker never asks, and does not stop a selector inside it from asking.

So one player message is asked about once when it is sent. When its reply is deleted and the player presses Send with an empty box, or Continue with a narrator in the group, Universe finds the unanswered message and asks again with the same number, so the narrator answers a `Narrator:` message as it did the first time, and a plain message goes to a character chosen with the narrator hidden. Regenerate asks again with the same number too, when it reaches the fallback and no reply survives between that message and the replies Vocalia deletes (see above).

Empty Send follows the same blank-reply rule as Continue. Vocalia's recovery counts a blank reply as an answer and then reports no unanswered message. When a player message is followed only by blank replies, Universe's recovery asks `firstSpeaker` with that message's number; if it names a member, the recovery returns that member alone in the shape Vocalia uses for a found message (`hasLatestUserMessage` true, that `sourceMessageId`, reason `empty-send-latest-user-universe-narrator`). Otherwise Vocalia's own result stands, and its empty-Send rules continue with the narrator hidden. Vocalia's empty Send reads only the `targets` and the `reason` of the result (lines 7503-7534); `hasLatestUserMessage` tells Vocalia's own empty-Send picker to stop there (line 3233).

With Vocalia's automatic turn flow off, a message is not asked about when it is sent, because Vocalia picks nobody then. It is asked about on each empty Send, and on each Continue with a narrator in the group, while it is still unanswered, and on each Regenerate that reaches the fallback while no reply survives between it and the replies Vocalia deletes.

When the opening, continuation or empty-Send picker, or the Regenerate and Continue fallback, finds no one and the narrator is the only present or remote member, the narrator is chosen, so a player alone with the narrator always gets an answer. The recovery leaves this to the empty-Send picker that calls it.

The reason strings are kept in one frozen object, `universeReasons`, at the top of the fragment. The reasons that reach Vocalia's empty-Send, Continue and Regenerate flows keep its `empty-send` and `controlled-` prefixes, because Vocalia lets those flows run when its automatic turn flow is off only for reasons with those prefixes (lines 5290-5307).

A reply with no character block (8122), a blank reply (8095), and a reply Vocalia refuses as an extra or bypassing generation (8172, 8184) never reach it, and neither do the other blocks of a reply with several.

`leaving=` is not one of Vocalia's parameters. Universe asks Vocalia's own `isOwnerEligibleForStateTransitions` (line 4768) before Vocalia applies the reply, which is the check Vocalia makes at line 5105.

## Vocalia faults Universe works around

- **Continue always targets message 0.** Vocalia's Continue button sits outside any chat message, so `getMessageIdFromDomElement` gives no message number (line 6714), and `Number(null)` turns that into 0 (lines 7055-7057). Vocalia's own Continue therefore makes the speaker of message 0 talk, usually the first character greeting, whatever the chat ends with; with the narrator at message 0, the narrator would answer plain messages. The `findLastAssistantMessageId()` branch of the same line shows what was meant. Universe's `resolveContinueTarget` fixes this only in groups with a narrator; without one, Continue behaves as Vocalia's own, bug included.

## How the tests run the real Vocalia

`tests/vocalia-overrides.test.mjs` builds in memory the text the build produces (the installed `index.js`, renamed, with the fragment appended) and runs it in a `node:vm` context against a stub SillyTavern context: a group of Narrator, Collette, Lize and Viola, a chat, `chat_metadata.aspect_vocalia` and the extension settings. Tests built on the helpers `sameAsVocalia` and `variants` run each scenario on Vocalia's own text as well: without `universeNarrator`, the result and the chat state must be identical to Vocalia's own, and with it the test checks Universe's result, often against Vocalia's. The other real-layer tests (the `leaving=` parser, the departing narrator, the prompt refresh, the Continue cases with a speaker who is no longer eligible, the Continue on an unanswered `Narrator:` message after a cast reply, the narrator alone or a lone `Narrator:` message, the blank-narrator empty Send, and the Regenerate cases driven through Vocalia's own `handleVocaliaControlledGeneration`) check Universe's result, some against a single run of Vocalia's own text. In the Regenerate test chats every reply, greetings included, carries its own `extra.gen_id`, as SillyTavern's do, so Vocalia's deletion window is the one a real chat gets; one case leaves `gen_id` out to pin the wider window.

A `node:vm` script cannot contain `import`, `export` or `import.meta`. Only for this test, and never in the build, the in-memory text gets these anchored changes and no others:

1. The import from `'../../../../script.js'` is removed. Its lines are kept empty, so line numbers stay as in Vocalia.
2. The import from `'../../../extensions.js'` is removed the same way.
3. `export` is removed from `export async function onEnable(`.
4. `export` is removed from `export async function onDisable(`.
5. `import.meta.url` (line 9028, in `loadVocaliaManifestMetadata`, which only the settings page calls) is replaced with a string.
6. `'use strict';` is added in front, as a module would be strict.

Each of the five replacements must match exactly once. If one does not, the test fails and names it, so a new Vocalia version that moves them shows up as a clear failure.

The context provides the names the imports gave Vocalia (`importedGetContext`, `importedExtensionSettings`, `importedSaveSettingsDebounced`, `importedDeleteLastMessage`, `importedFindExtension`), `jQuery` as a function that never runs its callback, `$` returning an empty selection, empty `Element` and `HTMLElement` classes so Vocalia's checks for page elements find none (a test that clicks a message builds an `Element` with a message number), a silent `console`, and a `setTimeout` that never fires, so Vocalia's trigger queue stops at its first wait instead of calling SillyTavern. `deleteLastMessage` removes the last chat message, and the group is already in Manual mode, so Vocalia's own `handleVocaliaControlledGeneration` runs end to end up to that wait. The context's `Math.random` and `Date.now` return fixed values, so the random fallbacks and the timestamps Vocalia writes are the same on every run.

## Checking a new Vocalia version

1. Install the new package, then run `tests/vocalia-overrides.test.mjs` on its own. It reads the installed Vocalia and fails when a renamed function is no longer declared exactly once, when a Universe name collides with a Vocalia name, when an anchored change above no longer matches exactly once, or when a scenario no longer behaves as described here.
2. Run the build. It stops on any name it cannot find exactly once.
3. Read the new version of each function in the table above and every caller of the five pickers, and check:
   - the return shape of each picker is the same (the overrides keep it);
   - Continue still resolves its message the same way (line 7056) and still writes a new message; if the message-0 fault is fixed, Universe's `resolveContinueTarget` may no longer be needed;
   - `findLatestUserMessageBefore`, `findLastAssistantMessageId` (still skipping blank replies) and `resolveMessageTargetOwner` still decide what a player message, the last non-blank reply and its owner are, and Regenerate still reaches the fallback only for a reply whose owner is not a group member;
   - Regenerate still deletes the messages `getTailRegenerateDeleteWindow` gives, and `isBlankAssistantMessage` still decides what a blank reply is;
   - no new rule in a picker reaches eligibility without `getRouteEligibleMembersCompat`, `isMemberRouteEligibleCompat` or `findMentionedPresentMembers` (for example by calling `getRouteEligibleMembers` or `isAvatarRouteEligible` directly);
   - no new picker exists, and no new code path applies presence changes from the player's message outside the two functions overridden for that;
   - `validTargetsFromBlock` still resolves `speakingTo` with `isUserAlias` and `getMemberByName`;
   - unknown parameter keys still reach the parsed block raw, malformed replies are still marked `routingMalformed`, a departing reply still reads as `departing` and an idle one as `idle`, and `isOwnerEligibleForStateTransitions` is still the check that refuses an absent owner;
   - the summon path still refreshes the prompt, Status panel and saved state after `setPresence`;
   - the `empty-send` and `controlled-` reason prefixes still decide what runs with automatic turn flow off.
4. Update the line numbers in this file.
